# 统一八问验证门

正式漏洞报告和提交前使用本表。所有问题统一采用正向问法，通过答案均为“是”，每题附证据位置和简短理由；信息不足写“待补证”，不把希望得到的答案当作证据。原第三问“是否需要靠假设解释危害”已改为正向表述。

| 编号 | 统一问题 | 通过标准（回答“是”并附证据） |
|---|---|---|
| Q1 | 资产、方法和验证操作是否在已确认的授权范围内？ | 写明资产、授权依据及本次允许的方法。 |
| Q2 | 是否有完整、可重复的 PoC？ | 提供真实请求或适合该技术的复现步骤、测试前提、角色、预期与实际结果；说明攻击前提可以现实满足。 |
| Q3 | 危害解释是否由已观察证据支撑，关键环节均已核实？ | 列明证据和因果关系；不依靠尚未验证的假设补齐攻击链。 |
| Q4 | 所声称的影响是否已经证明？ | 说明已验证的操作、数据或权限后果，以及仍未验证的边界。 |
| Q5 | 是否证明了安全边界被突破的结果？ | 有基线或负面对照，能够区分真实结果与反射、状态码、错误提示等单一现象。 |
| Q6 | 开发者能否理解危害和复现步骤？ | 用清楚的语言说明根因、操作步骤、证据位置和修复方向。 |
| Q7 | 是否能用具体业务场景说明影响对象和影响方式？ | 明确角色、资源、业务流程与已证实的影响范围；少量样本不直接证明全部用户受影响。 |
| Q8 | 当前证据是否符合目标项目的有效漏洞与拟报等级标准？ | 核对项目规则、已知/重复问题与设计行为；按已证明影响给出 P1/P2/P3 或对应等级的依据，不保证平台接受。 |

八题全部通过才进入正式漏洞报告。任一题未通过或待补证，保留 triage 笔记、缺口和下一步；有具体研究价值的线索继续遵循[价值与时间规则](../../bug-bounty/references/value-and-time.md)，需要加时就在聊天中申请。已证伪的候选记录原因；未立即证明影响本身不构成终止研究的理由。时间审批只改变预算，资产范围、方法和数据上限继续遵守行为准则。

取证遵循[行为准则](../../../CODE_OF_CONDUCT.md)：自有/合成数据优先；授权验证确有必要时，同一漏洞累计最多获取 5 条真实信息，取得足够证据即停止。凭据和秘密不作为读取样本，禁止批量提取。请求、响应和截图允许脱敏，保留字段结构、角色关系、关键差异与复现方法。

## 记录格式

逐题记录 `question_id`、`answer`（是/否/待补证）、`reason`、`evidence_path`。另记录 `finding_id`、`real_record_reads`、已验证影响、剩余缺口和下一步。报告等级只能对应已证明的影响。

## 旧检查项的归属

授权与根因范围归 Q1；复现与现实前提归 Q2；因果与完整链归 Q3；影响证明归 Q4；对照与真实结果归 Q5；表达清晰归 Q6；业务场景归 Q7；重复、设计行为、项目排除项和等级依据归 Q8。其他技能引用题号时使用此表。四项提交前检查作为整理证据的辅助清单，不另设一套问题编号。
