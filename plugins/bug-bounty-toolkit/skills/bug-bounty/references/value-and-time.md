# 网站价值分类与时间安排

这是逐站收集、选站和漏洞研究共同使用的规则。开始选站、切换研究方向或恢复任务时读取本文件，并沿用当前队列和计时记录。用户本轮明确指定的范围、方法、时间预算优先；本文件协调其他技能中的选站评分与研究时间建议。请求超时、工具运行时长、报告检查估时另行记录。

## 1. 价值分类

保留用户的原有分级，优先 Tier 0 / Tier 1：

| 分级 | 用户定义 |
|---|---|
| Tier 0 | RCE、认证绕过/账户接管、管理员权限、跨租户数据访问、严重权限提升、支付逻辑绕过。 |
| Tier 1 | 高价值越权、敏感数据泄露、关键业务流程绕过、身份控制缺陷、SSRF。 |
| Tier 2 | 普通权限问题、低敏数据暴露。 |
| Tier 3 | 低价值配置问题，默认忽略；能直接链到实际业务影响时重新评估。 |

这些定义用于评价研究线索。为网站安排顺序时，使用已观察到的业务、角色、数据和可研究入口给出暂定 `value_tier` 与 `value_reason`；在理由中写明具体入口、待核对的影响和证据位置。网站价值与已确认漏洞等级分别记录，最终严重性仍需验证。

例如：有实际订单/支付状态流的入口，可围绕支付逻辑提出 Tier 0 研究方向；含敏感账户或订单对象的查询接口，可提出 Tier 1 方向；只观察到低敏数据或普通权限边界，可列为 Tier 2；仅有低价值配置观察且没有业务影响链，可列为 Tier 3。登录页、管理员页面名称、框架名或域名关键词本身不足以认定高价值线索。多业务网站按当前有证据支持的最高价值研究方向排序，新增证据后更新分类。

信息不足时标记 `unknown`，先补充基础分类，并在覆盖记录中保留待办。范围、在线状态、业务类型和价值分级分别记录；401/403、静态页、网络失败不直接决定价值分级。

## 2. 队列选择

1. 对范围内站点建立基础记录，按已允许的方法核对归属、在线证据与业务类型。
2. 可执行的研究方向按 Tier 0 → Tier 1 → Tier 2 → Tier 3 排序；同级优先已有具体线索、合法测试条件和明确下一步的站点。`unknown` 单独保留分类待办，不能因未知被当作 Tier 3 丢弃。
3. Tier 3 保留基础收集结果，通常将进一步漏洞研究记为 `deferred`，写明低价值理由；出现直接业务影响链时重新入队和分级。
4. 分类与时间只调整顺序和深度。每个子站保留执行结果、受阻原因或延期理由；换方向后继续其他可执行队列项，不能将未处理项标记为完成。
5. 收集任务仅整理线索与后续计划。用户要求进入测试后，才执行相应验证；价值分级不会自动触发漏洞扫描。

## 3. 时间安排

原规则按工作阶段和线索安排时间；各 Tier 使用同一套阶段规则。

| 阶段/触发条件 | 时间安排 | 必须记录的动作 |
|---|---|---|
| 轻量启动 | 30 秒～1 分钟 | 写明当前站点、核心业务、钱/数据/权限等主要影响、优先研究方向与下一步。这是计划估时，资产收集和理解完整业务另行记录。 |
| 遇到异常，插队快验 | ≤3 分钟 | 用本轮允许的最小方法核对异常，记录结果，再返回原方向或评估深挖。收集模式下只核对收集信息。 |
| 探索方向连续无进展 | 20 分钟时复盘 | 记录当前证据、卡点和下一步；考虑换接口、业务方向或站点。若有具体理由继续，写明延长理由、预计投入和下一检查点，并遵守本轮总预算。 |
| 高价值线索进入深挖 | 预计 30～45 分钟；时间盒最多 45 分钟 | 先宣布线索、理由和预计投入；追踪完整数据流、根因扩散及影响链，按证据决定继续或收束。 |
| 深挖时间盒到期 | 可再申请延长一次 | 预计时间不足且判断该方向值得继续时，主动在聊天中向用户提出加时申请：提供已有证据、剩余具体问题、申请时长和预期结果。申请时长由本次说明并由用户确认；已有明确批准则沿用。等待时暂停该方向，继续其他独立可执行工作。 |

“进展”指新增证据让业务模型、边界、假设、复现或影响判断更明确；重复同一请求或相同失败结果不重置无进展计时。20 分钟是复盘触发点，不能仅因经过 20 分钟就丢弃正在取得证据的方向。深挖达到时间盒后，按收束或一次延长流程执行；改名、换参数、重新进入模式不能重置同一线索的时间盒或延长次数。

深挖触发信号：可控制的 ID/金额/状态字段、暴露其他用户/资源标识、前后端校验不一致、数据多接口流转、明显状态机、已复现异常但影响未完全确认。发现信号后立即评估其研究价值、测试条件与下一步，进入时输出：

```text
[进入深挖模式]
站点：<origin>
价值分级：<Tier 与证据理由>
线索：<具体入口/现象>
理由：<待核对的业务影响>
预计投入：30-45 分钟（本次计划 <具体分钟数>）
```

深挖必须追踪：核心数据 → 入口与可控制字段 → 存储/格式 → 处理与转换 → 展示/消费 → 输出/退出；同时检查二次使用与跨接口流转。仅有字段或页面线索时，如实保留未验证状态。

## 4. 逐站计时与恢复

使用实际时间工具或运行环境读取时间，不根据文字长度估算已用时；可以提前完成，无需等满时间盒。时间盒是 Codex 执行中的检查规则。长命令采用分段输出或有限超时，在返回控制后检查时间与进展。

在 `site-queue.csv` 增加 `value_tier`、`value_reason`、`current_mode`、`lead_id`、`started_at`、`elapsed_work_seconds`、`last_progress_at`、`planned_minutes`、`extension_count`、`extension_status`。日期时间带时区；未开始字段留空、累计时间和延长次数为 0。`current_mode` 可为 collection、exploration、deep；`lead_id` 标识同一研究线索，恢复时沿用。`extension_status` 使用 not_requested、pending、approved、denied、used；同一深挖线索提出一次延长申请后 `extension_count=1`，继续等待或记录用户决定，不能重新申请以绕过次数。每次恢复先读队列及进度，保留既有计时与延长状态。

在 `progress.jsonl` 追加 `timestamp`、`hostname`、`origin`、`action`、`value_tier`、`value_reason`、`current_mode`、`lead_id`、`depth_level`、`chain_potential`、`elapsed_work_seconds`、`brief_result`、`next_plan`，计时事件另含本段开始/结束时间、计划时长、检查点与延长次数。需要区分 `direction_elapsed_seconds`、`no_progress_seconds`、`deep_elapsed_seconds` 与 `paused_seconds`，避免探索耗时、深挖时间盒和等待时间混算。

记录分类/重分类、开始/恢复、异常快验、20 分钟复盘、进入深挖、暂停、延长申请/批准/拒绝、收束和换方向。等用户、等待外部 ARL 任务、挂起时单独记录暂停区间；累计站点工作时间保留已投入时间，当前研究方向的计时按活动区间累计。深挖耗时从宣布进入模式后累计，之前探索耗时保留在站点总投入中；批准延长后保存明确的新截止预算，在同一线索上累加耗时。每项研究结束写明证据、未解决问题及队列状态；未完成的站点仍保留后续计划。

加时聊天示例：“这个方向已确认 <证据>，还需要核对 <问题>。我预计再需要 <分钟数>，完成后可以判断 <具体结果>。是否同意加时？”用户明确同意后记录批准的时长，再继续该方向；等待期间暂停该方向并处理独立任务。时间批准不增加真实信息的 5 条上限。

## 5. 因时间未完成的候选

每次因时间停止该方向前，按[待续测表](time-deferred-findings.md)保存候选、已观察事实、存在可能性及理由、八问缺口、剩余步骤和预计续测时间。渗透结束必定输出全表与 CSV；没有条目也输出零结果。用户选择哪些编号继续并批准新预算后恢复，沿用原编号、范围、审批和[不同真实记录台账](real-records.md)。
